Unit 04

Turn completed work into reusable knowledge and tools

Turn completed work into reusable knowledge and tools. We'll introduce progressive disclosure for tools and large markdown files, then we'll see how it works out in practice. Includes written material, updated source code drop and optional practice

At the end of the previous live session we ended up with a working code repository, within which we were able to implement a new feature in a controlled way using progressive disclosure. Putting all the required information in auditable documents and scripts allowed us to see exactly what is going on, how agents load information and how the context is being organised. This also enables later inspection and improvement.

The mental model at this point looks like this:

We have a single repository, with doc tree hierarchy at the root. It describes architecture, approaches and product requirements. Requirements are captured in the executable specs that are followed by the implementing code.

All that forms a conceptual pyramid that organizes how information is generally loaded in the context of any agent operating in the repository.

In the next two units we’ll talk about scaling this approach in 3 directions:

  • adding custom CLI tools
  • introducing markdown outlines to work efficiently with large files
  • introducing concept of a control center to manage work across multiple code repositories

The resulting mental model will grow up and show how we can scale things up, if needed:

While doing that, we’ll continue using core principles from the previous units:

  • progressive disclosure approach stays, we just add one more “hop” at the top and one more level of detail at the bottom (CLI tools and outlines)
  • there still will be zero skills (we control context layout, while setup remains portable across harnesses)

Let’s get started!

Adding an outline tool

During the previous live session we’ve decided that it would be nice to introduce a better tooling to work with large markdown files without loading them entirely into the context. This will demonstrate how we can support:

  • dedicated tools and commands;
  • larger documents.

How do we do that? Let’s circle back to the order in which agents load content in their context:

  1. automatically load AGENTS.md and read it
  2. execute tree docs to get a map of the repository.
  3. dive into the relevant files in folders

so the tree docs is clearly the extension point. In our sample codebase the output of the command looks like this:


docs
├── behavior.md
├── features
│   └── release_a_seat.md
├── modes
│   ├── document_writing.md
│   ├── piecemeal_growth.md
│   └── workbench_notes.md
├── product.md
└── specifications.md

3 directories, 7 files

That looks nice and uses very few tokens:

But probably we could do a bit more.

What I would like to do next is to change the output of tree docs to make it more helpful to the agents, while keeping context use roughly the same. I would like the output of doc tree to also show:

  1. available tools with their usage;
  2. size of existing md files - hinting agent whether it should load file entirely or get its table of contents first.

Let’s start from the output. For example, this variant looks rather nice to me:

docs/
  behavior.md - 6 kB
  features/
    release_a_seat.md
  modes/
    document_writing.md
    piecemeal_growth.md
    workbench_notes.md
  product.md
  specifications.md - 6 kB
  tools/
    outline.py FILE - show markdown outline with line ranges (use for large files)
    tree.py - show docs and tools inside docs folder

The output stays rather compact (89 tokens), but it:

  • includes tools along with the brief help text
  • hints at large files by showing their size
  • allows adding more tools and documents as needed (it isn’t hard-coded)

The next step is to actually change tree docs to print that text. This is easy, since actually code agents don’t care if they have to execute tree docs or python3 my_tree_script.py.

So we can just copy-paste the desired output to Codex and ask to implement such script (e.g. in docs/tools/tree.py) that will provide a better version of tree docs, while highlighting large files and printing the first line of each Python script’s module docstring.

Once that is done, we could ask to write another script, called docs/tools/outline.py that would take a Markdown file as an argument and list its headings and their inclusive line ranges as another tree.

Once the scripts are done, we can try running them ourselves:

and then try running the outline tool as well:

So we get a very nice progression: first agents scan the documents in a repository as a tree, where each node can be addressed individually. Then they can optionally scan outlines of large markdown files as a tree, where each node is also addressable via line numbers.

On each level agents can perform efficient discovery first, followed by the selective reading. This comes naturally, since we make sure that our nodes are readable.

If you have used Company Brain technology of BitGN (e.g. by participating in the swarm experiment) and explored first stanzas that MCP delivers to agentic harness on startup, you would’ve noticed that it is a bit similar in structure - it delivers core instructions and a tree of workspaces/tools for further exploration.

All that remains - update AGENTS.md to point to the new way of getting our doc tree:

Always run `docs/tools/tree.py` at the start, use outline tool for ToC of large Markdown files. Before changing documentation read `document_writing.md`.

Adapting the codebase

Now we have implemented new functionality in the codebase. But, as it usually happens, perhaps the repository needs to be migrated or updated - in order to use this new feature consistently.

Let’s ask codex to review and suggest cleanups.

In my case codex suggested to:

  1. Make behavior and specifications more readable by introducing headings to structure content.
  2. Tweak AGENTS.md so that headings match content.

If you think about it - Codex is suggesting to make documents more readable for both humans and agents. It does that, because we introduced a tool that works naturally with the way we organize large documents.

If we look, for example, at the outline of the docs/behavior.md, it looks uneven, “Behavior contract” section contains a chunk of 5.5kB of text:

docs/behavior.md · 39 lines · 6,053 bytes
  # Behavior contract · L1–39 · 6,053 bytes
    ## Persistence boundary · L35–39 · 506 bytes

So let’s try checking out how Codex would carry out its own suggestions. It has piecemeal growth already loaded in the conversation, so it should be minimal:

And the behavior file now looks more reasonable as well, giving agents an overview of all features in a product for free:

docs/tools/outline.py docs/behavior.md

Now let’s see if the agents actually use this feature in daily work.

It will show better for large documents which create context pressure, so I’ve added transcript from the unit3 live video to the codebase under records/. It is structured using headings, so we can ask a question like: “records/ has 45-min video transcript about this codebase. What is it about?”

Here is what should happen:

  1. Codex should always start by executing the new enhanced doc tree to get high-level overview
  2. Within that overview it should discover the tool usage for outlining large files
  3. While searching for the information, it should use outline tool for the large files.

Here is how it goes:

  1. Codex executed tree.py at the start
  2. It read smaller files entirely
  3. It used outline.py tool for the initial discovery of larger files like behavior.md and the transcript

This looks good enough to proceed with the repo. All changes are available in the source code drop for this unit.

Although it already feels like this transcript shouldn’t really live in the codebase. Perhaps, it is a piece of information that relates to principles that cover multiple codebases? Self-check questions

  1. Take a look at the output of the two commands (in fact, try running them yourself in the terminal). Can you spot small hints in the output that work as a progressive disclosure and lead agents to discover more ways of working with the codebase, as they dive deeper? What are they? Why are they shaped this way? Why are they located on the lines where they are (and not earlier or later)?
  2. This progressive disclosure setup has a few gaps that will show up as the project grows more complex. How do you think, what are they?

Practical Exercise

Pick any agentic coding harness other than Codex. What would happen, when you give it a task below in this repository? First come up with your idea of how agent is going to work, then execute that agent and see if its sequence of action differs. Why does it differ?

Here is the task prompt:

I want to add a new feature into the codebase - workshop admin should be able to close and reopen reservations for a workshop. Closing blocks new reservations but preserves existing ones and allows releases. Reopening allows reservations when seats remain. Changing capacity does not reopen reservations. Plan the feature then implement it (with executable specs).
