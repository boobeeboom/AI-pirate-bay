Unit 01

Organize your codebase for agents

Organize a codebase so a fresh agent discovers and loads the context it needs, progressively.

I organize a codebase for the agents that will work in it. We are going to come back to the same repository over and over again. Each time, a fresh agent would need to re-discover relevant information, understand the task, and get to work using the proper tools.

To make that work well, it helps to look at what an agent is doing underneath.

An agent builds a conversation

An agent or agentic harness might sound complicated. But under the hood that is still a code that concatenates context and makes calls to a large language model.

Much of its work happens as a sequence: read the current context, decide what to do, call a tool, receive the result, and make another model call with that result in the conversation.

The interface of Codex or Claude can hide this from us, but an agent session is essentially an ongoing conversation that progressively builds its context. Tool calls can run in parallel, and long conversations can be compacted, but this sequence is a useful way to think about how an agent gets its work done.

Subagents are also a flavour of this workflow.

Things that we load early - shape decisions that follow:

  • which files the agent opens
  • what it considers a requirement
  • how it decides that the work is complete.

We want the relevant information to arrive before the decisions that depend on it.

When businesses adopt systems built on LLMs, one of the things they worry about is hallucinations. In practice, I pay attention to three failure modes (Hallucination triggers) that still apply to the coding agents:

  1. Not enough relevant information. The model has to work with gaps. It may make assumptions, go in circles, or produce something that does not fit the project.
  2. Too much irrelevant information. The facts we need are mixed with noise, old decisions, and material that does not apply to the task.
  3. A task that is too complicated. We need to split it into smaller pieces that the agent can handle and we can verify.

These are useful things to look for when a model gets something wrong; they are not an exhaustive explanation of hallucinations. They matter for a single model call, and they also matter for an agent making a sequence of calls over a growing conversation.

This is why I use progressive disclosure: load the relevant content as early as it is needed, and not much more. We can influence how the conversation develops by designing how the agent discovers the repository.

In this Module unit I’ll be talking mostly about the document side of the codebase structure for two reasons:

  • Documents and instructions are the most impactful part of the codebase, they get loaded into the context first
  • Code is important, but on a large scale it is less relevant than requirements and tests.

Still, the source code for this unit includes full executable project, so that you can actually try running it and seeing how these document decisions influence the agent.

The codebase is a book

Codebase is a book, and each agentic session is a new reader opening it. So we need to optimize the codebase for catching up fast.

This is where docs folder comes in. It acts as the index of the book. We control the names, the locations, and the instructions that tell the agent where to begin.

In the sample repository, AGENTS.md is the entry point. It gives the agent a few core principles and tells it to start by running tree docs. It also names the documents to read for the product vision, accepted behavior, and implementation mentality. Instructions for more specific work are conditional: before writing documentation, for example, read document_writing.md.

The first discovery step in the sample repo returns this:

This is a compact list of names and folders, it uses very few tokens. The agent can see what is available without loading the contents of every document.

I try hard to keep AGENTS.md small because it is part of the recurring starting context. It establishes the working context and points into the repository. The details can be disclosed when they become relevant. This is why tree docs instruction works so well.

A stable starting context can also benefit from prompt caching when the provider can reuse a matching prompt prefix. That can reduce processing cost and latency on repeat requests. OpenAI’s prompt caching guide explains the mechanism.

What do I put in AGENTS.md?

My aim is for AGENTS.md to fit on one screen. It contains the minimum that I want the agent to encounter first.

The sample for this module starts with a compact preamble:

This is a workshop reservation app.   
  
This is a web app using HTMX + Unix + Go + SQLite + Event-driven Specs (HUGSES) with modular monolithic architecture and stack flattening.

Source: AGENTS.md, lines 3–5

These keywords quickly give the agent an idea of the stack and my working preferences. I do not need to explain each technology there.

Then come the progressive disclosure instructions we have just seen: run tree docs, read the product vision, read the accepted behavior, and load the implementation mentality. The tree provides the index, the instructions provide a few hints on what to load and why:

Always run `tree docs` at the beginning to get an overview of durable documents. Before changing documentation read `document_writing.md`.

Read `product.md` for the product vision, `behavior.md` for the accepted contract, and `piecemeal_growth.md` for the implementation mentality.

Source: AGENTS.md, lines 9–11

The rest establishes a few priorities that come from how I work with agents.

Priorities for agents

These priorities come from how I work with agents. I do not want an agent inventing requirements, scaling for scenarios we do not have, or adding unit tests simply because unit tests can surely hurt nobody.

Rule 1: Do not multiply noise

Adding new text is less risky than removing text. It helps in thinking, and agents think by writing. So agents (Claude in particular) tend to add comments and explanations everywhere.

And removing text is risky - because there is a chance that we could throw out important requirements.

That means that code repositories tend to gradually keep on accumulating extra prose that will pollute contexts of all agentic session. I want to slow that process down. Hence the instruction to read writing_documents.md before changing anything. And that instruction tries to avoid the duplication and noise:

Follow the spirit of Unix when working with the documentation in `docs/` and comments:  
  
- document only things and surprises that would surprise an experienced engineer that knows all about NixOS, golang, Make and building web products like that.  
- When asked to update `docs/` and comments - bring them in sync with the project, removing stale things, updating surprises and removing obvious things.  
- Prefer descriptive filenames for files in `docs/`, for they are more explanatory when used with `tree docs`  
- Assume that the reader knows how to use grep and follow the links. E.g. instead of documenting makefile step in markdown, just mention it, same with the code.

Source: docs/modes/document_writing.md, lines 3–8

I’ll talk more about the Surprise/grep mindset below. For now just keep in mind that we pay attention to the Brandolini’s Law, when designing docs for agents that literally spend energy on dealing with bullshit:

The amount of energy needed to refute bullshit is an order of magnitude bigger than that needed to produce it.

Good naming of documents (also variables and classes) addresses the same “context noise is expensive” problem once over, from a different angle.

A longer, descriptive filename is cheap compared with loading a document to discover what it is about. The file index (e.g. output of a tree docs) should give the agent or human enough information to make that choice.

I introduce folders when there are enough files that grouping becomes useful. In my projects, the groups often include features, modes, personas and product documents. There is no need to create all of them in advance. Executable specifications live elsewhere, in specs/.

Because the document tree is loaded at the start of the session, internal instructions can refer to a document by its filename in backticks when that name is unambiguous. Otherwise, use a repository-root-relative path. For example, I do not need a full Markdown link to piecemeal_growth.md when the agent has already seen where it lives.

- Remember that full doc tree is always loaded in the context at the start of each session. So in instructions  refer to repository documents by filename in backticks when unambiguous in the doc tree, e.g. `prototype.md`. Otherwise use a repo-root-relative path without a leading slash, e.g. `docs/product/concepts.md`. Avoid Markdown links and `../` paths for these references.

Source: docs/modes/document_writing.md, line 9

I also keep a couple of personal writing preferences in document_writing.md: no manual line wrapping, and no tables unless asked. Hard wraps introduced around 80 characters were driving me crazy, so I wrote the rule once. Markdown tables are awkward for me to read without a renderer, so I prefer lists and prose. These are small instructions that keep the documents comfortable to work with.

- no manual wrapping of lines in MD files.  
- no tables (unless asked)

Source: docs/modes/document_writing.md, lines 10–11

Rule 2: Tests and specs are sacred

When working on projects I like to think of a pyramid of concepts that goes like this:

Most important things that go on the top usually have less content, are more important. I like even to write them by hand. This includes product vision or AGENTS.md. These are also the files that an agent tends to load first at the beginning of the conversation, thus applying their influence to every subsequent turn and decision.

As we go down the pyramid we get deeper into the details like requirements and tests. Requirements describe in human text what we want to capture. Tests or executable specs allow verifying that mechanically.

Code implementation sits at the bottom. If top of the pyramid is done correctly, then you could throw out the implementation and have agents rewrite that over the night.

I know that first-hand, since we’ve used to do that with a complex high-load e-commerce product in pre-ChatGPT era. Except humans were the ones rewriting the backend to meet new scalability standards. It works.

We’ll talk more about specs in later modules. The important part right now is this one: Tests/specs are more important than the code, they capture the requirements.

This means that if agent writes or modifies a test without asking me first - it makes a decision that will have a lasting impact on the code. If that decision is wrong, it will cripple the codebase.

Because of that:

Do not touch tests or executable specs without explicit permission. Tests and specs are requirements, when proposing one, explain the behavior it would freeze and its coupling to implementation.

Source: AGENTS.md, line 15

Rule 3: Don’t invent requirements

There is more subtle problem with agents that stems from the fact that they are running on LLMs that had a ton of written material to learn from.

These LLMs are like über-grandparents - they have seen a myriad of ways that things can go wrong. So naturally they want to protect us from the consequences at any possible way. This can be worth it when doing a security audit. When working on a prototype or drafting a feature - it will get in the way.

This is why I have a carefully crafted vector that I explicitly ask agent to load when working on the implementation - piecemeal growth or “don’t solve the problems that I don’t have yet”.

In the source code it reads as:

# Mode: Piecemeal Growth  
  
Piecemeal growth designs from forces that exist now: executable requirements, current workflows, and failures that have actually occurred. Like a desire path, the shape follows observed traffic; it is not paved in anticipation of journeys nobody has taken.  
  
In this mode, keep the implementation as narrow as the present contract. Do not add configurability, concurrency, fallback paths, validation, or abstractions for possible future uses. Make assumptions explicit and let violations fail loudly, so new pressure is visible instead of being absorbed by speculative machinery.  
  
When a new requirement or repeated failure appears, repair the design locally. Generalize only once reality has shown what the generalization must support.  
  
This is not an argument against integrity at real boundaries: protect durable data, external callers, security, and failures with demonstrated likelihood or cost. It is an argument against paying complexity for imagined ones.

Source: docs/modes/piecemeal_growth.md, lines 1–9

This mode, when loaded, tends to produce fairly compact changes in the code. The point is to work from the requirements we have, rather than optimize for a myriad of imagined scenarios.

Rule 4: Document the surprises

My starting rule is to document what would surprise an experienced engineer who already knows the stack. There is no need to explain how HTML works or how JavaScript is linked into a page. We can figure that out, and LLM was trained on that.

When an agent and I have discussed a lot of material, I find this a useful request:

Document only the things that were surprising to you.

It can produce a compact summary. When updating existing documentation, I ask the agent to bring it into sync with the project, remove stale material, update the surprises, and remove the obvious things. A lot of the work is cutting things out.

The same principle helps decide where information belongs. Ordinary implementation details can stay in the code. Surprising behavior or constraints specific to that code belong in nearby comments. Product purpose, customers, audience and underlying principles can live in documents, because the just implementation does not explain them.

Suppose we create a class and describe its fields in a separate Markdown document. Later, a refactor renames a couple of fields but leaves the document unchanged. Now we have two conflicting sources of information. Which one should the agent believe?

It is easier to keep the relevant explanation near the class and let the agent find and read the code. Agents know how to use grep and file tools! Repeating the implementation uses context and creates another representation we have to maintain. Hence the:

- Assume that the reader knows how to use grep and follow the links. E.g. instead of documenting makefile step in markdown, just mention it, same with the code.

Source: docs/modes/document_writing.md, line 8

Ideally, most of the code is so simple, boring and explanatory that it needs no comments.

I think of it as roughly 5% infrastructure and critical moving parts, and 95% straightforward code. That is my personal goal in projects, not a strict target, though.

Agent discovery in practice

For this example, I started a fresh agent in the sample repository with this task:

Explore this repository. Explain what users can do today, which features are only proposed, and how to run and verify the application. Keep the explanation short.

In this session, the repository’s AGENTS.md was already supplied before the task by Codex. There are also instructions and tool definitions supplied by the agent application, but AGENTS.md is the starting point we control inside the repository.

The most interesting part is how the agent went through our instructions:

Here is how it went:

The agent first ran tree docs and listed the repository files. It then loaded documents in a batch:

  • product.md: the product vision and scope.
  • behavior.md: the accepted behavior users can rely on today.
  • piecemeal_growth.md: the mentality for working on the implementation.
  • specifications.md: how the executable specifications interpret the accepted behavior.

Alongside those documents, it read the README.md, build and environment files, and relevant application code. It found how to run the application and how to verify it.

Note that Sol-6.1 in Codex also decided to cat AGENTS.md once more in the session, even though it had the same file already passed to it by the harness. Let’s call it a quirk.

Then it ran nix develop -c make check. While the checks were running, it continued reading source files. The checks passed, including 46 scenarios with 202 expectations, race tests, vet, and the build.

Two documents remained unopened: document_writing.md and workbench_notes.md. Their names were visible in the index, but their contents were not needed for this task. The agent was exploring and explaining the application; it was not writing documentation or workbench notes.

That is progressive disclosure in a real session. The docs tree exposed the available knowledge, while task plus entry instructions guided the following selection. The agent loaded the relevant documents together, followed through into the implementation, and verified what it could.

Along the lines we had our context organized neatly for us, top to bottom:

  • AGENTS.md
  • task
  • our index - output of doc tree
  • docs loaded from the doc tree according to the task
  • all other files and source code

Keeping the discovery path visible

Ability to audit progressive disclosure by my own eyes (or more frequently by Codex reading its own ~/.codex/sessions folder) allows me to see codebase efficiency and improve it. This is also why I prefer keeping project knowledge and reusable scripts in the repository over using various super tools and MCP servers.

Tools and skills can introduce another index, supplied by the agent application when a session starts. I have less direct visibility and control over how that catalogue is presented and how the agent chooses between it and our own documents.

With documents and scripts in the codebase, I can inspect the entry point, see the tree, change a name, move a document, and observe what a fresh agent actually loads. The knowledge and the means of acting on it live in a place we can manage together.

“we can manage together” is a polite version of saying to an agent to go review past sessions, suggest codebase improvements and then measure their impact on similar tasks.

It also lets us use the same project knowledge with different agents, including Codex and Claude Code.

Keep working records out of the normal reading path

As I’ve mentioned earlier, I like to think about the project as a conceptual pyramid. At the top are the purpose and context: what are we building, why, and for whom? Below that are more detailed requirements and features, then the code. I want the reading path to expose that context in a useful order.

That context is the state of the project/product that is true. However, documents can also include partially relevant documents like working plans and historical notes. They need to sit to the side to avoid adding noise to the primary working context.

I do not put every plan, prototype, or session note into docs/. That would gradually mix the current project knowledge with past ideas, changed decisions and various transient work.

Those materials go into records/. That folder has its own AGENTS.md, explaining that these are historical records, that they do not need to stay synchronized with the codebase, and that the agent should open them only when explicitly instructed.

For a complex feature, I might write a plan, follow a couple of steps, then abandon it and start another plan. If a later refactor renames a class, I do not want the agent updating every obsolete plan that mentions it. Those records describe the work as it happened; they do not all need to describe the current code.

Current requirements belong in docs/. A short proposed feature can also live there if we plan to work on it soon, with its status made clear. A more speculative possibility can stay in records/.

Practice: Try it with your agent

Start a new conversation in the sample repository and give the agent a real task. The orientation prompt above is one option. You can also ask:

What do I need to run the application locally?

Or:

Can you start the web server and show me around?

Or:

Explain the architecture. How is it working? What are the surprises and nuances?

When exploring a new codebase, I also like asking the agent to change something, just to see how that change impacts the codebase. We are working in a Git repository, so any changes can be discarded later.

I put a planned feature somewhere in the code (records/release_a_seat.md to be precise). So you can ask agent about it.

I want to implement that “release a seat” feature. Give me an implementation plan.

Alternatively you could ask the agent to write executable specifications for you to review or implement the entire feature and see how it goes.

Implement me “release a seat” feature

By the way, the proposal still has open decisions: what happens when there is no reservation, when the action is submitted twice, or when someone wants to reserve again?

A careful agent should not write any specs or tests without prior approval.

Keep in mind, that you do not need to understand every detail of the specification machinery yet. This exercise lets you see whether the discovery path gives the agent enough context to find the relevant instructions and proceed.

  1. Choose one task and inspect the conversation’s tool calls.
  2. Which documents did the agent discover? Which did it load?
  3. Did the agent find the commands it needed?
  4. Where did it miss something or read material that did not help?

You can also give the session link to a new chat that can inspect the original conversation and ask:

Look at how the agent in this session went through progressive disclosure. Explain how it discovered and loaded the relevant information, and where the reading path worked well or poorly. Session: SessionID, locate it in ~/.codex/sessions

You can get session ID by grabbing deep link of a session in Codex:

This answer could be used to optimise the progressive disclosure in the codebase. However, I would not reorganize a repository based on a single chat session. One conversation is useful for understanding how the path works. For broader changes, I look for repeated patterns across many sessions; the history of actual work gives us something to improve from. We will come back to those retrospectives later in the Module.
