Unit 05

Make the approach work in your own projects

Make the approach work in your own projects and scale with control centers. Discuss what needs adapting, and consolidate the takeaways. Includes wrap-up video.

Let’s wrap up this module and our journey of scaling AI Coding approaches.

In the previous unit we ended up in an awkward situation - we added a transcript of the webinar that describes approaches used in the codebase to the same codebase. It felt like a simple way to be able to tell an agent “Now let’s go through the transcript and see what else we can apply to our codebase”.

At the same time this feels slightly wrong:

  • webinars and conversations shouldn’t live in the code
  • different ideas, concepts or practices might actually be relevant to multiple repositories

This actually brings up another higher-level conflict. In AI Native coding setups we are going to have a mixture of various areas of knowledge and expertise that don’t cleanly map 1:1 to the code repositories. In fact, this is a mess:

For example, an IT department in a company might need to maintain a portfolio of services and codebases, trying to keep them up to date with the shared best practices, infrastructure approaches and documentation.

Likewise, in a product-oriented startup, the team might need to maintain a whole bunch of repositories around concrete deployments, but still collaborate on keeping them aligned with the product vision, shared DevOps practices and CI/CD processes.

Basically, regular codebases are organized around units of deployment or teams, while there always are cross-cutting concepts that are orthogonal to this setup.

So we need to move one level up. Thankfully, progressive disclosure can handle that.

My solution to the problem starts by figuring out areas of responsibility that we can capture cleanly in a separate repository, and then making that repository relevant to multiple codebases.

Since we’ve already started talking about applying principles from the AI Code Module 1 to multiple repos, let’s focus on that.

We’ll build ourselves a “Technical Excellence Control Center”. It will capture high-level insights from Module 1 and its sample project, allowing us to structure that information and apply it to other projects. Plus it will also demonstrate how Personal OS/Brain setups can be created.

Technical Excellence Center

So I would like to create a Git repo the whole purpose of which is to capture ideas about what constitutes “best practices” in AI Native Coding so far. The practices themselves will be replaceable (you could put in your own), but it will demonstrate how we can organize the repo.

Here is the layout of this repo, as printed by running docs/tools/tree.py:

You can immediately spot a few similarities and differences!

What is similar to a coding project:

  • we have the same docs folder with modes and tools.
  • AGENTS.md still points to the tools and instructs agents to scan the doc tree with tree.py on startup, while using outline.py for working with large Markdown files.

Here is how it starts:

# Technical Excellence Center

This control center helps us preserve engineering evidence, index useful sources, connect their stories, and deliberately apply practices across projects. `docs/` is its operating guidance; `00_inbox/` through `03_apply/` are its working memory.

Always run `python3 docs/tools/tree.py` at the start. Use `outline.py` to inspect large Markdown files, then read the relevant line ranges. Follow source references when the task needs evidence; do not load all incoming or captured material at startup.

Source: AGENTS.md, lines 1–5

What is different:

  • There is no source code in this repo (at least not yet)
  • Instead of the source code, we have 4 levels of information processing: inbox -> capture -> index -> apply. This structure is optimized for working with diverse information on the coding patterns & practices across multiple projects

Basically in this repository we keep core principles similar to those in the other repositories, but adjust the shape of the working memory to match the tasks at hand.

You already know from the previous units how docs, tools and progressive disclosure work. On top of that we introduce two concepts:

  1. ingestion pipeline (inbox -> capture -> index)
  2. project workspace (apply)

Let’s quickly go through these.

Ingestion Pipeline

The purpose of the ingestion pipeline is to allow adding a lot of raw information into the repository (things that we want to remember about a given topic), while minimizing context pollution and optimizing search.

I do it by adding a hierarchy of folders. They are even prefixed by numbers to make the order obvious.

  • 00_inbox - articles, transcripts and other things that we want to capture go here. This is a temporary staging ground
  • 01_capture - the source is preserved here unchanged, so we can return to what it actually said.
  • 02_index - each source gets a card that helps agents decide whether to open it and find useful passages. Arcs connect the evidence into evolving stories, including what remains unclear.

engineering_interests.md tells the agent which questions I care about when indexing sources. An arc can start with one source if it advances one of those questions; otherwise, a card is enough.

This is also how the ingestion pipeline in the Company Brain of BitGN is structured. It scales well to thousands of documents.

Now, let’s see how this ingestion pipeline works.

I’ve placed unit_03_walkthrough_transcript.md into the inbox and will ask Codex to process it.

While the process runs, see that our changes from the previous unit that were made in another repository work here as well:

  1. The agent starts work by executing tree.py. It will get a high-level overview and tool usage tips
  2. The agent loads core principles entirely, but then uses the outline tool to scan the 58 kB transcript before loading it.

I had to use the sentence “Don’t use yg” to avoid filing that webinar under a globally available workspace. You don’t need to mention that.

Once the work is done, we can review the changes:

So the agent:

  1. moved the source from the inbox into the capture folder.
  2. created a small index card that summarizes the transcript (it will help to scan information later)
  3. decided to start a new arc about spec-driven development, which is funny, since spec-driven development will be the focus of the next module.

The important part is that you don’t need to touch anything in the 02_index folder. It is maintained and used automatically by the agents. Just keep on adding relevant content.

To be more precise, agents update the index when asked to ingest, while people can check whether it remains useful.

By the way, here is one handy tip. You can easily capture web articles by installing the Obsidian Web Clipper extension and configuring your inbox folder to be the target for the capture.

But how would we use that content? Let’s move on to the heart of this control center - the project workspace.

Project Workspace

The idea of a control center is that agents could work freely across projects, carrying over information as needed. We no longer need to provide paths or point to the exact project.

Let’s give it a spin and show how this works by asking this question:

Look at the concepts and ideas from the last capture. How can we apply them to improve the webinar sample project? Offer me 3 small technical options under the piecemeal growth mentality.

Something interesting will happen:

First of all, Codex went on and figured out which capture we were talking about and which project.

Then it actually opened that project, oriented itself in it (nested progressive disclosure), loaded the product vision and figured out its structure.

Finally, it tried to ground insights from the webinar in the nuances of the project and offered the next three potential improvements.

Codex was able to do that because that other project is registered in this control center via a 03_apply/projects/ai_coding_sample1_webinars.md file that points to the project checkout and contains the following information:

# Workshop Reservations

- Checkout: `../ai_coding_sample1_webinars`, relative to this control center's root.
- Purpose: the AI Native Code webinar sample, a workshop reservation application used to demonstrate working with coding agents.
- Entry point: `AGENTS.md` in that checkout. Use its discovery instructions to find current product requirements, operating guidance, tools, and verification commands.

## Adoption notes

No practice adoption has been performed through this center yet. Existing project guidance remains in the project.

Source: 03_apply/projects/ai_coding_sample1_webinars.md, lines 1–9

When I decide that some concept is worth adopting as reusable guidance across my projects, I’d put it in 03_apply/practices/, with its source and where it applies.

The source for this control center is attached to this unit. To connect it to the sample project you would need to:

  1. put them both into the same folder
  2. make sure that the webinar sample project folder is called ai_coding_sample1_webinars (or update the reference to it)
  3. make sure that your agent can go outside the current folder, or just live dangerously and give it “Full Access”.

This setup now means that I can also ask Codex to register multiple projects there and start doing things like:

  • Hey, Codex, link the project from folder X in this control center (where we could be linking to another project of ours or adding the source code of a project that inspires us)
  • Look at project X and identify good solutions that match our engineering interests. What would you suggest adopting across our projects? Give me a numbered list.
  • I like your suggestions 3 and 5. Research them a bit and add them as practices to this control center
  • Go across our own projects and see where we can add practice 4 with minimal effort.
  • Look at my old project Y. It is really stale and needs to be brought up to speed. Compare it to project G, identify key missing practices and give me a prioritized list of what should be done.

You get the idea!

Practical Exercise

I would suggest grabbing this control center, installing it locally, then doing the following exercises.

  1. Capture an interesting article about coding that you heard about recently. See how it gets ingested, inspect the card and follow one reference back to the source.
  2. Link a few projects of yours to the control center. Or at least ask your agent to download and check out a known good-quality open-source project. Then launch your agent from the control center and ask to see how the insights from the last captured article could be applied to one of the linked projects.
  3. Choose one suggestion and explain why it fits the project. Ask your agent to apply it, then review the change and run the relevant checks. Record what improved or why no change was needed. If you changed guidance or discovery, try a fresh session directly in that project to see whether the agent finds and uses it.
