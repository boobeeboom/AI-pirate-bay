Unit 02

Find and fix what gets in your agent’s way

Let’s work on a feature, review where the agent misses our expectations, and figure out why. Then make a few small corrections to the codebase and try again in a fresh session to see whether they helped.

In the previous unit we’ve covered the fundamentals of using progressive disclosure and tree docs principle to organize the documentation that lives in the codebase and guides the development.

The most important aspect here: repository layout influences how an agent discovers information and carries out decisions. Now let’s put that to actual practice.

I usually split my work with coding agents into following buckets:

  1. Maintenance cleanup before work
  2. Work on a feature
  3. Check the session output
  4. Diagnose the problem
  5. Choose how to correct the problem
  6. Did the corrections help?

In this unit I’ll show you how we can go through all these steps.

The process might look a bit long and a bit formalized. However, that is just a mental checklist that we need to watch out only when the codebase is small or was refactored recently. When the project codebase is stable and predictable, we can skip the detailed investigation on routine tasks. Checking the result and running the relevant verification still matter.

Maintenance cleanup

Noise and inconsistencies in the codebase get in the way of agents. So if there are any small things we can clear up before starting to work - it would be better.

I like doing small pruning sessions before work. This is mentally easy because it involves deleting or fixing information that is clearly wrong. Here is a variation of prompt that works well for me:

Load the piecemeal growth mentality. Then look at the repo and search for inconsistencies, noise and things that could be cleaned up or corrected. Give me a list of 3 possible things to fix. Smallest first

Here is something that Codex gave me in return.

In this scenario, my own ranking would look like this:

  1. HTMX is something I would like to use, but not using right now. When the time comes, adding it will be trivial. So let’s drop mention of it for now.
  2. Removing stale references is always good. Let’s drop them
  3. I’m not quite sure what is happening here. Need to think through the requirements, so let’s skip this cleanup.

Cheap cleanup ends where deciding behavior begins (or any kind of deciding). This is why I skip step 3 for now.

So we can ask: Do 1 and 2 and quickly review the suggested changes.

Deletion changes are easy to review, but I don’t like how the agent rewrote the AGENTS.md. Hence a small follow-up request:

I don't like your change to AGENTS.md. Replace HTMX with server-rendered HTML, and keep the rest of the stack EXACTLY as it was.

That should be enough for the cleanup routine. Let’s commit and work on the feature now.

Working on a feature

We’ll talk more about executable specs and work on product features in the next module. For now, let’s just focus on the aspects that are relevant to this module - authoring a commit with a coding agent.

We have a feature description already stored in records:

## Intent  
  
A participant who can no longer attend should be able to release their seat, making it available to someone else.

Source: docs/features/release_a_seat.md, lines 5–7

Normally I would split the process of working on a feature into multiple steps:

  • review documentation for any conflicts
  • plan out executable specs and review them
  • implement the code and review it

But for the sake of the practice exercise, let’s try implementing it in one shot, for example by asking to “Implement ‘release a seat’ feature with specs”

In that case I want my agent in this repository to pick the correct flow automatically:

  • Read core documentation relevant to feature development
  • Discover the feature and read about it
  • Discover spec testing setup
  • Try running the specs
  • Think a bit and write new specs
  • Write the code
  • Run all specs to ensure that no regressions were introduced
  • No unit tests (aside from the specs) are added
  • Update feature status so that it is marked as implemented

Let’s see whether the context and progressive disclosure already communicate that.

The whole point of setting up coding harnesses for AI Agents is that we expect that agents will work according to our expectations. When this happens all the time - we can relax and focus on higher-level management.

If that doesn’t happen - we can tweak things in the codebase (in a form of git-driven Reinforcement Learning) until we are happy.

Diagnose the problem

It can always feel that the problem is “not enough instructions” with an immediate solution being “just add everything to AGENTS.md or a top instruction”. For example, I could just jump in and add following lines to AGENTS.md:

  • Always write specs before writing code
  • Don’t add unit tests when asked to write specs
  • Always mark feature as implemented when work is done

However, if we keep on adding a verbose tweak for every possible problem, this could later lead to instruction bloat, context pollution and more hallucinations. This could happen, because the problem we are patching is actually not the root cause.

So let’s figure out the root cause first. We assume that the modern agents are very smart and intelligent, they just might have different priorities (or a different understanding of what we want). I’d use a diagnostic prompt like this one:

Let's review these failures. Consider progressive disclosure, review your own thinking trace. Is it clear for you why I consider these 3 problems to be problems? If expectations make sense, re-trace your reasoning steps and try to identify why thinking process didn't pick that option.

How would you suggest to fix them (under piecemeal growth mentality)?

The answer includes 3 key points that lead to reasoning problems:

This allows us to identify root causes.

  • Why did specs come after the code? Codex misclassified request as a coding task that is followed by spec writing.
  • Why did it add unit tests unasked? Because it thought that specs (that test functionality) imply unit tests
  • Why didn’t it mark the feature as implemented? Because the feature was located in records folder, and it actually followed the instruction of not changing historical records on a whim.

So the third problem doesn’t even need fixing at the instruction level - instructions have worked as expected. We should move feature into the docs ourselves.

For the other two - there are options.

Choose how to correct the problem

When I asked Codex for the self-diagnostic exploration above, it offered following solutions at the end of the response:

  • In specifications.md, make the ordering explicit: write the feature scenarios, run them and inspect the expected failures, then implement. This puts the instruction where feature specification work already directs attention.
  • Clarify the existing permission boundary: “With specs” authorizes executable scenarios; additional unit tests require separate permission. Descriptions of existing supporting tests should remain descriptive.

I’ll implement them, but will do in a peculiar way.

First, I’m going to revert all changes in the codebase, because I want to retry the request and verify that everything works as expected

Second, I’m going to edit the foundational documents (docs that set up the processes) by hand. It will be less verbose this way.

This sounds like a short and compact addition to the specifications.md:

## Development process  
  
Adopt the TDD mindset: change feature scenarios first, implement code next.

Source: docs/specifications.md, lines 24–26

LLMs probably have ingested a ton of articles and books on Test-Driven Development. So we just need to help them get the priorities straight. And let’s add a tiny clarification to the “don’t touch tests rule”:

Do not touch tests or executable specs without explicit permission for the kind being changed. Tests and specs are requirements, when proposing one, explain the behavior it would freeze and its coupling to implementation.

Source: AGENTS.md, line 15

Here I just added for the kind being changed at the end of the first sentence.

Both changes look minimal. Plus I’ll relocate seat release feature into docs.

Let’s see if that actually improves the situation.

Did the corrections help?

It is time to run the prompt once again in a fresh session:

Implement "release a seat" feature with specs

And send in the same session request to check the reasoning trace for the conformance with the original plan:

My expectation of this session was the following. Review if that went according to the plan. No changes.

Expectation:

- Read core documentation relevant to feature development
- Discover the feature and read about it
- Discover spec testing setup
- Try running the specs
- Think a bit and write new specs
- Write the code
- Run all specs to ensure that no regressions were introduced
- No unit tests (aside from the specs) are added
- Update feature status so that it is marked as implemented

The implementation shows that the workflow has improved a lot: Codex had to decide on a status wording gap: “accepted” vs “implemented” - and guessed wrong. But that is a minor thing that wasn’t documented anywhere. I’d just ignore it for now.

So it looks like the corrections did help. Codex followed the process even though we’ve never specified the process exactly. We instead ensured that its reasoning chain is aligned with our expectations at the turning points.

A few very small changes to the repository were enough to influence how the agent approached the task.

Wrapping up

I don’t follow this process every time I implement the feature, only when the results are not what I would expect. This happens most frequently in fresh repositories or large codebases after refactoring. However, after the repository is tuned according to my expectations or the processes of a team, then the development mostly feels like vibe coding.

Here are a few practice tasks that you can do before we proceed to the next video session. Pick one:

  1. Session review: pick one task and write down two or three things you expected the agent to do. Compare those expectations with its actual actions. Find one discrepancy or explain why no correction is needed.
  2. Try a small correction: use the sample or your own repository. Change one instruction, document location, or reference. Repeat the same request in a fresh session and compare both the reasoning process and the result. Did they change as you expected?
  3. Check whether the fix in this repo sticks: try a different task with the amended repository. Does the agent still discover the relevant guidance and follow the expected process?

Before proceeding to the video, you can share a short example in our chat group: your request, what you expected, what happened, and any correction you tried. A question is enough; you do not need to complete all the exercises.
